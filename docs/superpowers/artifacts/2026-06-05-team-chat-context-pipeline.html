Team Chat Context Pipeline

Review luồng broadcast Team Chat, cách nạp context vào agent, trạng thái seen/reply và các risk cần chốt trước khi implement.

Kết luận review

Phương hướng triển khai trong plan là đúng: dùng Team Chat làm nguồn sự thật, tạo delivery request cho từng session member, nạp context vào session chat của agent, rồi bridge reply thường về lại Team Chat.

Ý chính

Cần bổ sung 3 điểm trước khi triển khai: định nghĩa rõ optional broadcast kết thúc bằng trạng thái nào, giảm kích thước context packet để tránh tốn token quá mạnh, và guard mapping reply khi một session nhận nhiều Team requests liên tiếp.

Phần đang đúng

Reuse team_mention_requests cho MVP là hợp lý, vì ta đã có lifecycle, status event, session card, no-action tool, auto-report bridge và namespace guard. Không cần migration DB ngay.

Điểm cần sửa trong plan

Plan hiện nói optional agent có thể “không gửi text answer”, nhưng nếu agent không gọi mark_team_mention_no_action thì request có thể kẹt ở delivered/seen. Cần có fallback hoặc quy ước terminal rõ ràng.

Pipeline tổng thể

Điểm quan trọng: Team Chat không gửi “chat text thô” sang agent. Nó gửi một envelope có metadata, behavior instruction, source message và context snapshot. Vì vậy agent có thể hiểu đây là Team mention hay Team broadcast.

Lý do không self-echo

Agent vừa tạo report đã có nội dung đó trong session riêng. Echo lại chính nó chỉ tốn token, làm nhiễu transcript và có thể tạo vòng lặp “mình vừa nói...” không có giá trị.

Context packet nạp vào agent

[HAPI_TEAM_MENTION]
requestId=<uuid>
teamChatId=<uuid>
sourceMessageId=<uuid>
deliveryKind=mention|broadcast
requiresResponse=true|false

Reply behavior:
- mention: You were directly mentioned and must respond.
- broadcast: Optional Team update. Reply only if useful.
- Normal text reply will be auto-posted to Team Chat.
- If no reply is needed, call mark_team_mention_no_action.

Token risk

Plan hiện dùng 20 recent messages và mỗi message có thể tới 2.000 ký tự. Nếu Team Chat có nhiều agent, cùng một context sẽ bị nhân lên theo số session. Nên cap lại theo mục tiêu: required có context rộng hơn optional; optional dùng compact context.

Agent response và auto-post

Privacy guard

Nếu user chat riêng với session sau một Team item, reply tiếp theo không được auto-post. Điều kiện bắt buộc: latest user turn phải có meta.sentFrom='team-chat' và teamMentionRequestId.

State machine seen / reply

Đề xuất semantics

Dùng no_action làm terminal state cho “đã seen và không cần reply”. Nếu chỉ để seen, request vẫn nằm trong active queue hiện tại và UX sẽ giống còn việc chờ xử lý.

Delta đã patch vào plan

1

Thêm semantics cho optional completion

Chốt rằng “seen thôi” trong UI tương ứng với terminal no_action ở backend. Nếu agent không reply, request không được kẹt ở active queue.

2

Giảm context cap

Thay cap 20 x 2.000 ký tự bằng profile riêng cho required và optional. Required cần nhiều context hơn; optional chỉ cần context đủ hiểu thay đổi mới.

tokenprompt
3

Thêm tests cho multi-request

Test một session nhận hai Team requests liên tiếp; plain reply chỉ auto-post vào latest request, còn explicit report_to_team(replyToRequestId) xử lý đúng request.

4

Đổi wording UI queue

Không gọi tất cả là “Team mentions waiting”. Dùng “Team items” hoặc tách “Mentions” và “Updates” để user hiểu optional broadcast không phải task bắt buộc.
